# 「三台设备」是怎么被数出来的——吉林农大校园网设备数限制机制研究

> 研究时间：2026-11-16，实测环境：macOS 客户端 10.7.224.192/16，Portal `http://202.198.1.80`（`SRunCGIAuthIntfSvr V1.18 B20191227`，portal 为 golang 版）。
> 标注规则：**【实测】**＝本次现场跑出来的结果；**【推断】**＝协议/架构推导，附验证方法。

---

## 0. 一句话结论

本校的"三台设备"限制落在**认证层（AAA 在线会话表）**，不是靠嗅探流量去数你有几台机器：

**一个终端 = 一个 DHCP 租约 = 一个内网 IP = 一条在线会话记录。**

第 4 个终端去做 Portal 认证时，AAA 先查该账号当前在线会话数是否已达产品配额（本账号 `products_name = 20元包月-学生`），超了就拒绝并回 `E2610`（在线设备数超限）。因此改 MAC、改电脑名、装不同浏览器都没用——被数的是会话/IP，不是设备指纹。

## 1. 现场证据

| 观测项 | 结果 | 说明 |
|---|---|---|
| 本机 `en0` MAC **【实测】** | `06:d4:86:ce:38:b5` | macOS 私有 Wi-Fi 地址（本地管理位，随机化） |
| 服务端 `rad_user_info.user_mac` **【实测】** | `06-D4-86-CE-38-B5` | 与服务端记录完全一致 |
| Portal 页 `#user_mac` 输入框 **【实测】** | `value=""`（空） | PC 浏览器 JS 根本拿不到 MAC，页面留空 |
| 内网地址 / 网关 **【实测】** | `10.7.224.192/16`，网关兼 DHCP 服务器 `10.7.255.254`（`c4:07:78:0b:a0:02`） | 典型 BRAS/AC 一台设备三种角色 |
| ARP 邻居表规模 **【实测】** | 685 条，无 AP 隔离 | 大二层广播域，AC 可以直接看全网的 MAC↔IP |
| DHCP 租约 **【实测】** | `11/16 12:00:35` → `11/22 12:00:35` | 每终端一个独立 IP，租约 6 天 |
| 出口公网 IP **【实测】** | `23.128.188.177` | 校园网出口统一 NAT |
| 出口 UA 是否被改写 **【实测】** | `httpbin.org/headers` 原样返回 `curl/8.7.1` | 目前**没有** UA 归一化/改写动作 |
| IPv6 **【实测】** | `en0` 只有 `fe80::` 链路本地 | 不存在"IPv6 每设备一个地址绕过配额"的路径 |
| 设备管理接口 **【实测】** | `rad_user_dm`，签名 `sha1(time+username+ip+unbind+time)`（见 `ref/jquery.srun.portal.js:317`） | 系统本身具备"按账号列出/解绑在线终端"的能力 |

关键推理：`user_mac` 有值而网页 `#user_mac` 是空的 ⇒ **MAC 不是客户端上报的，是 AC/BRAS 从二层 ARP/DHCP snooping 表里学来的**。这也解释了为什么"改浏览器 UA / 隐藏 MAC"这类操作对配额毫无影响。

另一个关键点：错误码 `E2620 = 该 IP 已在线` ⇒ 在线会话的**主键是 (username, 内网 IP)**，MAC 只是挂在会话上的属性字段。

## 2. 计数链路（谁在哪一层数）

```
终端A ─┐
终端B ─┼─ AP/交换机 ── BRAS/AC 10.7.255.254 ── AAA(深澜) 202.198.1.80 ── 出口 NAT 23.128.188.177
终端C ─┘   (DHCP snooping/ARP)   (分IP、发RADIUS计费)   (在线会话表 + 产品配额)
```

1. **二层接入**：AP/交换机维护 MAC↔IP（DHCP snooping / ARP 表），本网段 685 条邻居说明这个表是"全可见"的。
2. **BRAS/AC**：给每个终端分配独立 IP，向 RADIUS 发 `Accounting-Start`，携带 `Framed-IP-Address`、`Calling-Station-Id`（MAC）、NAS 端口。
3. **AAA（深澜）**：写在线会话表，一条会话 ≈ 一个终端；同时把 `user_mac` 记进属性（`rad_user_info` 能查回来）。
4. **Portal 认证时做配额判定**：`count(在线会话 where username) >= 产品配额` → 回 `E2610`，否则下发放行（CoA/AC 侧开权限）。
5. **可选的第二层——数据面共享检测（各校开关不同）**：TTL / UA 种类 / IPID / TCP 指纹(JA3) / 时钟偏移 / 并发会话数。这一层**不会**回 `E2610`，它的表现是"能上网但过一阵被踢、限速、弹共享提示"。

**所以先分清你被卡在哪一层**：报错 `E2610` = 配额层；能上网但莫名掉线 = 数据面层。这两层的对策完全不同。

## 3. 三个实验，把机制钉死（都在自己账号范围内，无损）

### 实验 A：验证配额维度（≈10 分钟）

1. 手机 A、平板 B、电脑 C 各自连 Wi-Fi、各自做 Portal 认证（不要开热点共享）。
2. 每登录一台，查一次会话：
   ```bash
   curl -s "http://202.198.1.80/cgi-bin/rad_user_info?callback=cb"
   ```
   看 `online_ip` / `user_mac` 是否变成新设备的值。
3. 第 4 台登录，记录返回码。
   - 预期 **【推断】**：返回 `E2610`，且 A/B/C 三台**不掉线**。
   - 若第 4 台登录成功而 A 被踢：配额是"后进先出替换"，不是硬拒绝。
4. 在第 4 台上把 Wi-Fi 私有地址换成另一个随机 MAC 再登录，结果不变 ⇒ 证明计数与 MAC 无关。

### 实验 B：验证有没有数据面共享检测（最省事的关键实验）

1. 只让电脑 C 一台做 Portal 认证。
2. C 开互联网共享（macOS「互联网共享」/ iPhone 个人热点 / OpenWrt 路由），其他设备全部走 C 的 NAT，**不再单独登录**。
3. 观察 30~60 分钟：
   - 稳定不断、`rad_user_info` 里始终只有 C 一条会话 ⇒ **没有数据面检测**，这条路就是最优解（只吃 1 个配额）。
   - 期间掉线/被踢/限速 ⇒ 有数据面检测，进实验 C。

### 实验 C：定位数据面检测的具体维度（单变量法）

一次只上一项，各观察 1 小时，谁让你稳定就是谁在起作用：

| 维度 | 特征 | 处理 |
|---|---|---|
| **TTL** | Windows=128、Linux/macOS/iOS/Android=64、部分网络设备=255，NAT 后同一源 IP 出现多种 TTL | 出口统一 `iptables -t mangle -A POSTROUTING -j TTL --ttl-set 64` |
| **UA** | 同一 IP 混着 Windows/Android/iOS 的 UA | UA2F（NFQUEUE 改 UA）/ 统一 UA |
| **IPID** | 同一源 IP 的 IPID 出现多条递增序列 | rkp-ipid 随机化 |
| **时钟偏移** | 各设备 NTP 漂移指纹不同 | NAT 劫持 123/UDP 到本地 NTP |
| **DNS / JA3 / QUIC** | DPI 指纹多样性 | 统一 DNS、关 QUIC、TLS 指纹归一 |

参考做法与踩坑记录：<https://www.cnblogs.com/aquawius/articles/16759604.html>、<https://catalog.chn.moe/技术/OpenWrt/为啥我的路由器会被检测到/>。

## 4. 三种可行做法（按省事程度排序）

### 做法 1：一台设备认证 + NAT（推荐，本仓库就是这个思路）
`menubar/` 的 Rust 托盘负责让**出口这一台**保持在线，其余设备挂在它后面共享。
- 收益：无论后面挂多少台，配额层只看到 1 条会话。
- 现状：本网出口 UA 未被改写 **【实测】**，若实验 B 显示不掉线，则连伪装都不用做。

### 做法 2：OpenWrt 做出口（最稳）

```bash
# TTL 归一
iptables -t mangle -A POSTROUTING -j TTL --ttl-set 64
# UA 统一（UA2F，走 NFQUEUE）
opkg install ua2f kmod-ipt-ipopt iptables-mod-ipopt
uci set ua2f.enabled.enabled=1 && uci set ua2f.firewall.handle_fw=1 && uci commit ua2f
service ua2f enable && service ua2f start
# IPID 随机化（rkp-ipid）
iptables -t mangle -N IPID_MOD
iptables -t mangle -A FORWARD -j IPID_MOD
iptables -t mangle -A IPID_MOD -j MARK --set-xmark 0x10/0x10
# NTP 强制本地，消除时钟偏移特征
iptables -t nat -A PREROUTING -p udp --dport 123 -j DNAT --to-destination 192.168.1.1
# 顺手把 DNS 收敛到路由器
iptables -t nat -A PREROUTING -p udp --dport 53 -j REDIRECT --to-ports 53
```

### 做法 3（反例，别做）
每台设备各自连 Wi-Fi 各自登录、或把路由器改成桥接让每台设备各拿一个 IP——后者反而**更快吃满配额**（这正是很多"共享检测破解教程"里说桥接解决共享检测、但配额照样爆的原因）。

## 5. 全是无用功的民间办法（以及为什么）

| 办法 | 为什么无效 |
|---|---|
| 改 MAC / 换私有 Wi-Fi 地址 | 配额按 (username, IP) 会话数，MAC 只是属性记录 **【实测】** |
| 改电脑名 / 换浏览器 / 清 Cookie | 认证不依赖这些 |
| 用不同 ac_id 或不同 SSID | 本网 `ac_id=4` 唯一，会话仍归同一账号 |
| 换用别人的账号 | 会撞 `E2606`（IP 已被其他账号绑定） |

## 6. 本次研究用到的探测命令

```bash
# 1) 查当前会话（会返回 user_mac / online_ip / 产品名 / 余额）
curl -s "http://202.198.1.80/cgi-bin/rad_user_info?callback=cb"

# 2) 取挑战串，确认 client_ip 与 srun 版本
curl -s "http://202.198.1.80/cgi-bin/get_challenge?callback=cb&username=<USER>&ip="

# 3) 设备管理接口（签名规则：sha1(time+username+ip+unbind+time)）
#    注意：unbind=0 的查询在本网实测返回 logout_ok 且会话 add_time 会被刷新；
#    unbind=1 为 MAC 解绑。勿在正在用的会话上反复调用。
python3 - <<'PY'
import time,hashlib,urllib.parse,urllib.request
U,IP="<USER>","<LOCAL_IP>"; t=int(time.time()); unbind=0
sign=hashlib.sha1(f"{t}{U}{IP}{unbind}{t}".encode()).hexdigest()
url="http://202.198.1.80/cgi-bin/rad_user_dm?"+urllib.parse.urlencode(
    {"ip":IP,"username":U,"time":t,"unbind":unbind,"sign":sign,"callback":"cb"})
print(urllib.request.urlopen(url,timeout=8).read().decode())
PY

# 4) 检查出口是否改写 UA（有改写说明学校在做 UA 侧处理）
curl -s https://httpbin.org/headers
```

## 7. 一页速查

- 你被数的是**会话**，不是机器；一条会话 = 一个 IP。
- MAC 是 AC 从二层 ARP/DHCP 表学的（`user_mac` 已被服务端记录 **【实测】**），改它无意义。
- `E2610` = 配额层拦截；能上网但掉线 = 数据面检测层。两件事，分开测。
- 最优解：一台设备认证 + NAT；有没有必要再做 TTL/UA/IPID 伪装，由实验 B 决定。
